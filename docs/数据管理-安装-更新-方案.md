# TBM Lite 用户数据管理 · 安装 · 更新 —— 设计方案

> 状态：待评审 | 适用版本：0.1.0 → 0.3.x | 决策依据见 §10 决策记录
>
> 决策基线（已确认）：更新通道 = **GitHub Releases**；用户数据位置 = **`%APPDATA%\TBM Lite`**；
> 备份档位 = **滚动自动备份 + 一键备份/恢复**；§9-② 其余安装项**默认全量纳入**（未明确否定）。

---

## 0. 设计原则

1. **用户数据与安装资源彻底分离**：安装包覆盖/升级**永不**触碰用户数据目录；用户数据目录里**不存放**任何程序资源。
2. **有版本、可回滚**：任何改变数据形态的动作（迁移、恢复、导入、更新）都必须「先备份、可判定、可回滚」。
3. **失败可解释**：数据相关失败必须落到 `app.log` 并在 UI 给出一句人话 + 一个动作（打开目录 / 恢复备份 / 重试）。
4. **单一权威路径**：所有路径从 `pathManager` 派生，禁止业务代码里再出现 `path.join(...)` 拼数据目录。
5. **写入原子化**：文件写入一律 `tmp → fsync → rename`；多表写入一律事务；跨文件系统操作先复制再切换。
6. **不做静默数据破坏**：删除类操作先进「回收站目录」，配置类写入先备份旧文件。

## 2. 总体架构：三层模型

```
┌── 层 1：安装资源（只读，随安装包覆盖） ──────────────────────────┐
│  <install>/resources/app.asar          # dist + dist-electron     │
│  <install>/resources/publish/          # 仅「模板/默认值」种子    │
│      config/aj-api.example.json        # 无任何真实 Key           │
│      README-DATA.txt                                              │
└───────────────────────────────────────────────────────────────────┘
                    │ 首启 / 新版本补齐（仅当目标文件不存在）
                    ▼
┌── 层 2：用户数据（权威，可备份可迁移，升级不动） ────────────────┐
│  %APPDATA%\TBM Lite\                                              │
│      .meta.json      app.db  app.db-wal/-shm                      │
│      files/  config/  logs/  backups/  tmp/                       │
└───────────────────────────────────────────────────────────────────┘
                    ▲
┌── 层 3：临时/缓存（可随时删除，不入备份） ───────────────────────┐
│  %APPDATA%\TBM Lite\Cache\ + tmp\   （Electron 自带 Cache/GPUCache）│
└───────────────────────────────────────────────────────────────────┘
```

**分层规则**

| 规则 | 说明 |
|---|---|
| R1 | 层 1 只读；程序**永不**写 `resources/` |
| R2 | 层 2 是唯一事实来源；备份/恢复/导出只针对层 2 |
| R3 | 升级 = 覆盖层 1，层 2 原样保留 |
| R4 | 卸载**默认保留**层 2；删除需用户显式确认（§4.4） |
| R5 | 种子文件仅在「目标不存在」时落地；用户改过的配置永不被种子覆盖 |

## 3. 用户数据管理

### 3.1 权威路径（`electron/utils/paths.ts` 重构）

```ts
// 决策优先级：TBM_DATA_DIR 环境变量 > portable 标记 > 默认 userData
class PathManager {
  private root!: string;
  private isDev = !app.isPackaged;

  /** 必须在 app.whenReady() 之前完成 root 解析（portable 模式需 setPath） */
  init(): void {
    if (this.isDev) {
      this.root = path.join(APP_ROOT, "electron", "app-data", "dev");
    } else if (process.env.TBM_DATA_DIR) {
      this.root = path.resolve(process.env.TBM_DATA_DIR);          // 测试/企业定制
    } else if (fs.existsSync(path.join(path.dirname(app.getPath("exe")), "portable"))) {
      this.root = path.join(path.dirname(app.getPath("exe")), "data"); // 便携（P3 可选）
      app.setPath("userData", this.root);
    } else {
      this.root = app.getPath("userData");                          // %APPDATA%\TBM Lite
    }
    this.ensureLayout();
    this.adoptLegacyLayout();   // <root>/publish/* → <root>/*（0.1.x 已有安装）
  }

  getRoot()        { return this.root; }
  getDbPath()      { return path.join(this.root, "db"); }
  getSqliteFile()  { return path.join(this.root, "db", "app.db"); }
  getFilesRoot()   { return path.join(this.root, "files"); }
  getTrashRoot()   { return path.join(this.root, "files", ".trash"); }
  getConfigPath()  { return path.join(this.root, "config"); }
  getLogsPath()    { return path.join(this.root, "logs"); }
  getBackupsPath() { return path.join(this.root, "backups"); }
  getTmpPath()     { return path.join(this.root, "tmp"); }
  getMetaFile()    { return path.join(this.root, ".meta.json"); }

  /** 所有「渲染层可影响」的路径必须经此收敛 */
  resolveWithin(base: string, relative: string): string {
    const abs = path.resolve(base, relative);
    const rel = path.relative(base, abs);
    if (rel.startsWith("..") || path.isAbsolute(rel)) {
      throw new Error(`非法路径：${relative}`);
    }
    return abs;
  }
}
```

**要点**

- `db/index.ts` 改为 `createClient({ url: pathToFileURL(getSqliteFile()).href })`，**彻底消除相对路径语义**。
- 目录布局：

**门禁规则（`electron/core/data-guard.ts`）**

| 场景 | 行为 |
|---|---|
| `schemaVersion === CURRENT` | 正常启动 |
| `schemaVersion < CURRENT` | 走迁移（§3.4） |
| `schemaVersion > CURRENT` | **拒绝启动写入**：模态框「数据由更高版本（1.2.0）创建」+ 三个动作：① 退出 ② 从备份恢复 ③ 打开数据目录；进程以只读模式运行或直接 `app.exit(1)` |
| `appVersion < minReaderVersion` | 同上（旧版程序拒绝写入） |
| 无 `.meta.json` + `app.db` 存在 | 视为 0.1.x 数据 → 探测 `PRAGMA user_version`（=0）→ 标记为 v1 并补齐 meta |
| `cleanExit === false` | 记 `warn`，执行 `PRAGMA quick_check`；异常则提示恢复备份 |

### 3.4 迁移框架（替代裸 DDL）

```
electron/db/migrations/
├── index.ts        # runner
├── 001_init.ts     # 现有 4 表（等价于当前 migrate.ts）
├── 002_pragmas.ts  # 索引 + user_version 基线
├── 003_fk_cascade.ts        # 重建 xqab_t 带复合 FK ON DELETE CASCADE
└── 004_attachment_refs.ts   # ffff_t PK 改 (ffff001,ffff002,ffff004) + 引用计数
```

```ts
// electron/db/migrations/index.ts
export interface Migration {
  version: number;                 // 目标 user_version
  name: string;
  up(ctx: { db: LibSQLDatabase; sql: typeof sql }): Promise<void>;
}

const CURRENT_SCHEMA_VERSION = MIGRATIONS.at(-1)!.version;

export async function applyMigrations(db: LibSQLDatabase): Promise<void> {
  await db.run(sql`CREATE TABLE IF NOT EXISTS schema_migrations (
    version INTEGER PRIMARY KEY, name TEXT NOT NULL,
    applied_at TEXT NOT NULL, app_version TEXT NOT NULL, checksum TEXT NOT NULL)`);

  const { user_version } = (await db.get(sql`PRAGMA user_version`)) as { user_version: number };
  const pending = MIGRATIONS.filter((m) => m.version > user_version).sort((a, b) => a.version - b.version);
  if (!pending.length) return;

  // ① 迁移前强制备份（VACUUM INTO，见 §3.5）
  const backupPath = await backupManager.create(`pre-migrate-${user_version}-${pending.at(-1)!.version}`);
  logger.info({ from: user_version, to: CURRENT_SCHEMA_VERSION, backupPath }, "开始数据迁移");

  for (const m of pending) {
    try {
      await db.transaction(async (tx) => {          // DDL 也可在 SQLite 事务内
        await m.up({ db: tx, sql });
        await tx.run(sql`INSERT INTO schema_migrations (version,name,applied_at,app_version,checksum)
                         VALUES (${m.version}, ${m.name}, ${now()}, ${app.getVersion()}, ${checksum(m)})`);
        await tx.run(sql`PRAGMA user_version = ${sql.raw(String(m.version))}`);
      });
      logger.info({ version: m.version, name: m.name }, "迁移步骤完成");
    } catch (err) {
      logger.error({ version: m.version, backupPath, error: String(err) }, "迁移失败，回滚到备份");
      await backupManager.restoreFrom(backupPath, { skipPreBackup: true });
      throw new DataFatalError("数据迁移失败，已回滚到迁移前状态", { backupPath });
    }
  }
  await meta.update({ schemaVersion: CURRENT_SCHEMA_VERSION });
}
```

**约定**
- 迁移**单向只增**；禁止修改已发布迁移文件；改动即新增版本号。
- 每个迁移必须：① `IF NOT EXISTS` 幂等 ② 可在空库上跑通 ③ 附带 `scripts/verify-migration.ts` 断言（行数、抽样字段）。
- 需要「重建表」时按 SQLite 官方 12 步：建新表 → 拷数据 → 建索引 → 删旧表 → 改名 → 校验 → `foreign_keys` 开关前后处理。
- 开发期流程：改 `schema.ts` → 新增 `00X_*.ts` → `npx tsx scripts/migration-self-test.ts`（在 tmp 上对 dev 库副本跑一遍 + 校验）。
- `PRAGMA foreign_keys` 必须在事务外切换；`data-guard` 启动顺序：`journal_mode=WAL` → `busy_timeout=5000` → `foreign_keys=ON` → `applyMigrations` → 一致性巡检。

### 3.5 备份与恢复（档位 1：滚动自动 + 一键手动）

**统一入口 `electron/services/backup-service.ts`**

```ts
export interface BackupEntry {
  id: string; file: string; kind: "auto" | "manual" | "pre-migrate" | "pre-restore" | "pre-import";
  sizeBytes: number; createdAt: string; appVersion: string; schemaVersion: number;
}

export const backupService = {
  /** 唯一正确的 SQLite 在线备份方式：VACUUM INTO（一致性快照，含 WAL 内容） */
  async create(kind: BackupEntry["kind"], label?: string): Promise<BackupEntry> {
    const dir = kind === "manual" ? pathManager.getManualBackups() : pathManager.getAutoBackups();
    fs.mkdirSync(dir, { recursive: true });
    const file = path.join(dir, `${kind}${label ? "-" + label : ""}-${stamp()}.db`);
    if (fs.existsSync(file)) fs.unlinkSync(file);            // VACUUM INTO 要求目标不存在
    await db.run(sql`VACUUM INTO ${sql.raw(`'${file.replace(/'/g, "''")}'`)}`);
    const entry = { id: path.basename(file), file, kind, sizeBytes: fs.statSync(file).size,
                    createdAt: new Date().toISOString(), appVersion: app.getVersion(),
                    schemaVersion: await currentSchemaVersion() };
    await writeAtomic(path.join(dir, path.basename(file) + ".json"), JSON.stringify(entry));
    logger.info({ entry }, "创建备份");
    return entry;
  },

  list(): Promise<BackupEntry[]> { /* 扫 auto+manual 目录读 .json 侧车，按时间倒序 */ },

  prune(): Promise<void> {
    /* auto: 每日首个保留 30 天；总数上限 20；超限删最旧（连 .json 一起）。
       永不动 manual。pre-* 备份在「一次成功启动且 quick_check 通过」后降级为普通 auto。 */
  },

  /**
   * 恢复备份（设计稿）。
   * ⚠️ 实现时修正：libsql 原生客户端在 Windows 上 close() 后仍持有文件句柄，
   *    本进程内无法删除/重命名 app.db。实际实现为「两阶段恢复」：
   *    阶段一 校验 + 预备份 + 拷到 tmp/pending-restore.db + 写标记；
   *    阶段二 下次启动、尚未建立数据库连接时换库，然后 relaunch。详见 §11。
   */
  async restoreFrom(backupFile: string, opts: { skipPreBackup?: boolean } = {}): Promise<void> {
    await maintenance.runExclusive("restore", async () => {
      if (!opts.skipPreBackup) await backupService.create("pre-restore");
      assertIntegrity(backupFile);                 // 只读打开 + PRAGMA quick_check
      const target = pathManager.getSqliteFile();
      const stage = path.join(pathManager.getTmpPath(), "restore", "app.db");
      copyAndVerify(backupFile, stage);            // 复制 + 大小/hash 校验
      await dbClient.close();                      // 释放句柄
      for (const f of [target, target + "-wal", target + "-shm"]) rmIfExists(f);
      fs.renameSync(stage, target);                // 同分区 rename 原子切换
      await meta.update({ cleanExit: false, lastRestoreAt: new Date().toISOString() });
    });
    app.relaunch(); app.exit(0);                   // 重启，让新库在干净进程里加载
  },
};
```

**触发点与保留策略**

| 触发 | 类型 | 说明 |
|---|---|---|
| 当日首次成功启动后 | auto | 每自然日 1 份 |
| 迁移前 | pre-migrate | 不可裁剪，直到迁移成功 + 一次干净启动 |
| 恢复前 | pre-restore | 不可裁剪（保留 5 份） |
| 旧数据导入前 | pre-import | 保留至导入验证通过 |
| 退出时（当日有写入） | auto | `before-quit` 中同步等待（超时 5s，超时则放弃并记日志） |
| 设置页「立即备份」 | manual | 永不自动删除 |

> **附件是否进备份**：档位 1 仅备份 `app.db`。UI 必须写明「备份不含附件文件；附件为内容寻址只增不改，删除会进 `files/.trash`，可通过『打开数据目录』取回」。若后续升级到档位 2（ZIP 导出），实现见 §9 延伸项。

**损坏自愈**
- 启动：`PRAGMA quick_check`（上次 `cleanExit=false` 时）+ 打开失败（`SQLITE_CORRUPT/NOTADB`）→ 弹窗「数据库损坏」→ 提供「从最近备份恢复」+「另存损坏库用于分析」。
- 恢复失败（备份也损坏）→ 逐个尝试更旧备份（最多 5 份），全失败则提供「新建空库并保留损坏库副本」的最坏路径。

### 3.6 完整性与原子性

| 项 | 措施 |
|---|---|
| PRAGMA 基线 | `journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`、`foreign_keys=ON` |
| 多表写 | 全部进 `db.transaction`（`deleteRequirement`、`syncItems`、`importFile`+引用、`createRequirement`） |
| 文件写 | `tmp/` 内写完 `fsyncSync` → `renameSync` 覆盖（config、sessions、meta、备份侧车） |
| 一致性巡检 | `core/integrity.ts`：① 悬挂明细（无主档）② 无主附件记录（`ffff002` 拆分后无对应 `xqaa_t`）③ 孤立物理文件（`files/**` 未被 `ffff_t.ffff003` 引用）④ 明细 seq 重复。启动快速跑（>5 万行则改为抽样/异步），设置页「立即检查」可全量跑 |
| 软删除 | 删除的物理附件移入 `files/.trash/<ts>/`；配置类改动保留 `<file>.bak` |
| 审计 | 删除/恢复/导入/重置四类操作写结构化审计行到 `logs/audit.log`（保留 90 天） |

### 3.7 附件存储改造（修复 D10）

现状：`ffff_t.ffff004`（hash）为 PK + `deleteFile(hash)` 直删文件 → 去重语义与引用语义冲突。

**目标模型**

```sql
-- 004_attachment_refs.ts
CREATE TABLE ffff_t_new (
  ffff001 TEXT NOT NULL,   -- 归属表名 xqaa_t
  ffff002 TEXT NOT NULL,   -- 归属主键 'pj|req'
  ffff004 TEXT NOT NULL,   -- sha256
  ffff003 TEXT NOT NULL,   -- 存储相对路径 xqaa_t/<hash>.<ext>
  ffff005 TEXT NOT NULL,   -- 原始文件名
  ffff006 TEXT NOT NULL,   -- 扩展名
  ffffcrtdt TEXT NOT NULL, ffffecrtid TEXT NOT NULL, ffffstus INTEGER NOT NULL,
  PRIMARY KEY (ffff001, ffff002, ffff004)     -- 同一文件可被多处引用
);
```

- `import` 改为 `INSERT ... ON CONFLICT DO NOTHING`（同需求书重复上传同一文件 → 幂等）。
- `deleteFile` → `detach(tableName, ownerKey, hash)`：删**引用行**；若无任何剩余引用 → 物理文件移入 `.trash`（引用计数式删除）。
- `deleteRequirement` 内改为 `detachByKey` 后仍走同一事务。
- `ownerKey` 拼接禁止 `|`：`project-service.createProject` / `requirement-service` 校验 `pjaa001/xqaa001` 不含 `|` 与路径分隔符（现在含 `|` 会串键）。
- 附件 GC（手动 + 每日一次）：`files/**` 减去 `ffff_t.ffff003` 集合 → 移入 `.trash`；`.trash` 超 7 天删除。
- 打开/另存：`resolveWithin(getFilesRoot(), rel)` 后再做 `fs.realpathSync` 二次校验，拒绝符号链接逃逸。

### 3.9 安全与隐私

**① 移除内置共享密钥（D1，最高优先）**

1. 从仓库与安装包删除真实 Key：`electron/app-data/publish/config/aj-api.json` → 换成 `aj-api.example.json`（空值 + 注释字段）。
2. **吊销并轮换**该 Key（已推送 GitHub，必须视为泄漏）。
3. 清理 git 历史：`git filter-repo --path electron/app-data/publish/config/aj-api.json --invert-paths`（或 BFG），强推后通知协作者重新 clone。
4. `.gitignore` 增补：`electron/app-data/**/config/aj-api.json`、`electron/app-data/**/db/`、`*.db`、`release/`。

**② 密钥加密存储**

```ts
// electron/services/config-service.ts
const ENC_PREFIX = "v1:";                      // safeStorage(Windows DPAPI, per-user)
function sealKey(plain: string): string {
  if (!plain) return "";
  if (!safeStorage.isEncryptionAvailable()) return plain;   // 降级：明文 + UI 警告
  return ENC_PREFIX + safeStorage.encryptString(plain).toString("base64");
}
function openKey(stored: string): string {
  if (!stored?.startsWith(ENC_PREFIX)) return stored;
  return safeStorage.decryptString(Buffer.from(stored.slice(3), "base64"));
}
```
- 读取兼容：旧版明文 Key 首次加载时透明升级为密文并重写文件（写前 `.bak`）。
- DPAPI 密文与 Windows 用户绑定 → 备份/迁移到别的机器后 Key 不可解 → 检测到解密失败时提示「API Key 需重新填写」，其余数据不受影响。

**③ 默认「首启自填」**
- 首启向导第 3 步引导填写（或「稍后设置」）；未配置时 AI 功能入口给出明确引导而非抛错（当前 `loadConfig` 直接 `throw`，体验差）。

**④ 日志脱敏**
- `logger` 增加 `redact(obj)`：键名匹配 `/token|key|secret|password|authorization/i` → 只留 `前4位***`；禁止打印 `ANTHROPIC_AUTH_TOKEN` 全量。
- 需求书正文/明细不出现在日志（当前 `search-agent` 若打 prompt 需一并收敛）。

**⑤ 数据外发告知**
- 首次使用 AI 功能（解析/AI 搜索）弹一次性确认：「需求书内容将发送至你配置的第三方 AI 接口」；设置页可查看/重置该确认；提供「禁用云端 AI（仅保留本地功能）」开关（`config/app.json: aiEnabled`）。

## 5. 更新（electron-updater + GitHub Releases）

### 5.1 通道与发布流程

| 通道 | 来源 | 用户可见性 |
|---|---|---|
| `stable` | GitHub Release（非 pre-release） | 默认 |
| `beta` | GitHub Release（pre-release） | 设置页手动开启 |

- **发布流程（GitHub Actions）**：`git tag v0.3.0 && git push --tags` → CI：`npm ci` → `npm run build` → `electron-builder --publish always`（带签名 Secret）→ 产出 `Setup.exe` + `.blockmap` + `latest.yml`/`beta.yml` → 自动创建 Release（附 CHANGELOG 段落）。
- 仓库若为 **private**：需在客户端内置 Token（不可接受）→ 改用 `provider: generic`，feed URL 指向「内网静态服务器」或「GitHub Release 资产的公开镜像 URL + 自建 `latest.yml` 托管」。此项在发版前必须确认仓库可见性（见 §10 待决项）。
- 版本号同步：`package.json.version` 是唯一来源；构建时写入 `app.getVersion()` 与 `.meta.json`，并在 `CHANGELOG.md` 记录「是否含 schema 变更 / 最低支持版本」。

### 5.2 客户端状态机

```
idle ──(启动 10s / 每 6h / 手动)──▶ checking ──▶ not-available ─▶ idle
                                     │
                                     └─▶ available ─▶ (autoDownload: 后台下载) downloading(progress%)
                                                          │
                                                          ├─▶ downloaded ─▶ 用户操作
                                                          │       ├─「立即重启安装」→ 备份 → quitAndInstall
                                                          │       ├─「稍后」→ autoInstallOnAppQuit=true，退出时安装
                                                          │       └─ 退出时静默安装
                                                          └─▶ error ─▶ 指数退避重试（最多 3 次：5s/30s/2min）→ 记录并提示
```

| 配置 | 值 | 理由 |
|---|---|---|
| `autoDownload` | `true`（默认通道 stable） | 减少用户等待；`beta` 通道同样 true |
| `autoInstallOnAppQuit` | `true` | 用户「稍后」后仍能收敛 |
| `allowPrerelease` | 按通道 | beta 通道可测 |
| `allowDowngrade` | `false` | 禁止降级写入旧 schema |
| `fullChangelog` | `true` | 展示完整更新日志（渲染 Markdown） |
| 检查时机 | 启动后 10s + 每 6h + 手动 | 避免启动争抢 IO |

### 5.3 数据安全护栏（更新链路的硬约束）

1. **更新前**：`download` 完成 → 用户点「立即重启安装」时，main 进程：
   `await maintenance.runExclusive("pre-update")` → `backupService.create("pre-update")` → 写 `.meta.json.lastUpdateFrom = app.getVersion()` → `autoUpdater.quitAndInstall(true, true)`（静默 + 自动重启）。
2. **安装后首启**：`cleanExit` 必为 false（安装器强杀）→ 走 `data-guard`：`quick_check` → `applyMigrations`（自带 pre-migrate 备份）→ 成功则更新 `.meta.json.appVersion/schemaVersion`，并把 `pre-update` 备份标记为可裁剪（保留最近 2 份）。
3. **回滚预案**：
   - ① 保留上一版安装包到 `backups/app/<version>/TBM Lite-...-Setup.exe`（可选，体积换安全感）；
   - ② 恢复 = 卸载新版 → 安装旧版 → 启动 → 若旧版拒绝打开（schema 更高）则从 `pre-update` 备份恢复；
   - ③ 文档给出《回滚手册》（含「先备份当前数据目录」这一步）。
4. **CI 硬门禁**：若某版本的迁移不可逆（`minReaderVersion` 提升），Release Notes 必须显式标注「升级后不可降级」，并将该版本列入强制更新判定。

### 5.4 版本门禁与强制更新

```ts
// 随安装包内置的兼容矩阵（也可由远端 update.json 覆盖，签名校验后生效）
const POLICY = {
  minSupportedVersion: "0.2.0",     // 低于此版本必须升级（存在已知数据风险）
  forceBelow: "0.2.5",              // 低于此版本：仅允许「立即更新」，不能「稍后」
  minReaderVersion: 2,              // 能打开当前数据目录的最低版本
};
```

- 远端 `update.json`（发布到 Release 资产或静态托管）可下发策略；**必须**与 `latest.yml` 同级、经 HTTPS 获取，并校验 `signature`（签名阶段启用）。
- 强制更新 UI：模态框（不可关闭）+「立即更新」；`mainWindow.on("close")` 在 `forceUpdating` 期间 `event.preventDefault()`。
- 数据门禁与更新门禁联动：若本机 `schemaVersion` 使 `appVersion < minReaderVersion` 不成立，则正常启动；若用户手动降级安装旧版，旧版 `data-guard` 会拒绝写入并引导（§3.3）。

### 7.1 启动序列（`electron/main.ts`）

```ts
    await applyMigrations(db.raw);            // 迁移（含 pre-migrate 备份）
    await backupService.onAppStart();         // 每自然日 1 份 auto 备份 + prune

    await meta.markBoot("appVersion", app.getVersion());
  } catch (err) {
    return showFatalDialog(err);              // 不进入主界面，避免带病运行
  }
  registerHandlers();
  createWindow();
  updateService.init();                       // 10s 后首次检查

// ③ 退出：有写入则备份，标记 cleanExit
let quitting = false;
app.on("before-quit", async (e) => {
  if (quitting) return;
  e.preventDefault(); quitting = true;
  try { await backupService.onAppQuit(); } finally { await meta.markCleanExit(); app.exit(0); }
});
```

### 7.2 维护互斥（`electron/core/maintenance.ts`）

```ts
let tail: Promise<unknown> = Promise.resolve();
let activeTag: string | null = null;

export const maintenance = {
  isActive: () => activeTag !== null,
  async runExclusive<T>(tag: string, fn: () => Promise<T>): Promise<T> {
    const run = tail.then(async () => {
      activeTag = tag;
      broadcast("maintenance:state", { active: true, tag });
      try { return await fn(); } finally {
        activeTag = null;
        broadcast("maintenance:state", { active: false, tag });
      }
    });
    tail = run.catch(() => undefined);       // 不因失败卡死队列
    return run;
  },
};
```

### 11.5 安全事件处置记录（API Key 泄漏）

**根因**：真实 Key 被写在 `electron/app-data/publish/config/aj-api.json`——该目录同时是安装种子
（`electron-builder.json5` 的 `extraResources`），所以它看起来像「配置模板」而被提交；
原 `.gitignore` 只忽略 `app-data/dev/{db,files,logs,chat-sessions}`，未覆盖 `publish` 与 `config`。
该文件在初始提交 `e1f0361` 中进入历史，而仓库为 **public**，因此 Key 公网可读。

**已处置**

| 步骤 | 结果 |
|---|---|
| 当前版本移除真实 Key，仅保留 `aj-api.example.json`（token 为空） | ✅ |
| `.gitignore` 覆盖 `app-data/**/{db,files,logs,config/aj-api.json,.meta.json,backups}` | ✅ |
| Key 改由 `safeStorage(DPAPI)` 加密存储 | ✅ |
| `git filter-branch` 从全部历史中删除两个 `aj-api.json` + `reflog expire` + `gc --prune=now` | ✅ 本地对象库已无该字符串 |
| 强推远程 `main`（`e1f0361 → 043c366`、`eb2d4e3 → 86ce764`） | ✅ 分支上文件 404 |
| 旧 TBM 仓库排查（pickaxe 搜索） | ✅ 未泄漏 |

**残留风险与待办**

1. **GitHub 侧不可达对象仍可按旧 SHA 读取**（实测 `ref=e1f0361` 仍返回 HTTP 200）：
   force-push 只移除分支引用，不会删除服务端不可达对象。任选：
   - 删库重建（该库 0 fork / 0 star / 2 个提交，代价极小，可彻底清除）；或
   - 找 GitHub Support 代为清理缓存对象。
2. **必须吊销并轮换原 Key**（唯一能真正止损的动作，不依赖建库操作）。
3. 本地开发数据目录 `app-data/dev/config/aj-api.json` 仍为旧明文 Key（已不再被跟踪）；
   轮换后在「设置」页保存新 Key 即会加密覆盖。

**结论**：在完成第 2 步（轮换）后，第 1 步的残留对象已不构成实质风险（只剩无效字符串），
但建议按需执行删库重建以消除扫描噪音。
